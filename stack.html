Technology Stack

Tools, frameworks, and infrastructure choices behind the IDS and Implementation systems, and the documentation hub itself — with the reasoning behind each decision.

Intelligent Design System (IDS)

IDS

The platform used by programme design teams to design villages, set input targets, and produce Section Two planning documents.

React + TypeScript
Frontend
Web application for village design, data uploads, input allocation, and document generation.
Why: Component model maps well to the IDS workflow wizard; TypeScript catches data contract errors early in a domain with complex nested input schemas.
Node.js + TypeScript
Backend
REST API backend handling data processing, user management, and Section Two document assembly.
Why: Consistent language across the full stack. Reduces context-switching and allows shared type definitions between frontend and backend contracts.
IDS Prediction API (Python)
ML Service
Machine learning model that predicts household agriculture value (USD) for Year 1 and Year 2 from survey inputs. Exposes a REST API at ids.api.nonproftinnovations.io.
Why: Python is the standard for ML model serving. Isolating the model as a separate service means the backend can call it without coupling the prediction logic to the main codebase.
Postman
API Docs
Postman collection documents the IDS backend API. Shared with the team as a published collection.
Why: The team already uses Postman for manual testing. Reusing it as documentation avoids maintaining a separate spec format.
Implementation System

Implementation System

The field operations platform — mobile app for data collection, web dashboard for management and reporting, and a distributed microservices backend.

Flutter + Dart
Mobile App
Cross-platform mobile application for field data collection — works on Android and iOS from a single codebase.
Why: Single codebase for Android and iOS eliminates duplication. Flutter's offline-first architecture and local SQLite support are critical for field workers who operate with intermittent connectivity.
React + TypeScript
Web Platform
Office-facing dashboard for programme oversight, analytics dashboards, VSF approvals, and user management.
Why: Consistent with the IDS frontend stack. Large ecosystem for data visualisation components needed for dashboards.
PHP / Laravel
Backend (11 services)
11 Laravel microservices, each owning its domain — User, Profile, Training, Agriculture, VSLA, DataMongo, Livestock, Leadership, Check-in, Workplan, Notification.
Why: Laravel's Eloquent ORM, built-in queue integration, and Swagger generation (l5-swagger) make it productive for API-first microservice development. Mature ecosystem for the complex domain logic this system requires.
RabbitMQ
Message Queue
Async message bus for event-driven communication between services. Services publish domain events; the DataMongo service subscribes and builds the analytics read store.
Why: Decouples domain services from the analytics layer — services don't need to know about downstream consumers. Queues absorb traffic spikes from bulk field data uploads.
MySQL
Primary Database
Relational write store for all domain services. Each microservice has its own MySQL database (database-per-service pattern).
Why: ACID compliance required for financial data (VSLA savings, VSF loans). Separate databases per service enforce domain boundaries and prevent cross-service data coupling.
MongoDB (DataMongo)
Analytics Read Store
Aggregated read store populated via RabbitMQ events. Serves all web dashboard queries and analytics endpoints.
Why: Document model matches the denormalised structure needed for fast dashboard queries that span multiple domain entities. Separating read and write stores (CQRS pattern) keeps analytics queries from competing with write throughput.
Redis
Cache
In-memory cache for frequently accessed data — user sessions, permission checks, and hot analytics queries.
Why: Reduces repeated database round-trips for session validation on every API request. Critical at scale when thousands of field submissions arrive during programme windows.
Kubernetes + Tyk Gateway
Orchestration
3-node Kubernetes cluster with HAProxy/Nginx load balancing. Tyk API Gateway routes requests to microservices by path prefix. Each service runs at 3 replicas.
Why: 3-replica deployments allow rolling updates without downtime. Tyk centralises authentication, rate limiting, and routing without coupling this logic into each service.
AWS S3
Object Storage
Database backup storage. MySQL backups are exported and uploaded to S3 on a scheduled basis.
Why: Durable, geographically-redundant off-server backup storage. Lifecycle policies automatically expire old backups and reduce cost.
Loki + Promtail + Grafana
Logging
Centralised log aggregation. Promtail collects logs from all containers and ships to Loki; Grafana provides querying and dashboards.
Why: Lighter-weight than the ELK stack for this scale. Log labels enable efficient filtering by service and environment without full-text indexing overhead.
Swagger (l5-swagger)
API Docs
Auto-generated Swagger UI for all 10 backend microservices. Annotations in the PHP source code are compiled into an OpenAPI spec at build time.
Why: Documentation stays in sync with the code — annotations live next to the endpoints they document. No separate spec maintenance required.
GitHub Actions
CI/CD
Automated testing, security scanning, and deployment pipelines for all system components.
Why: Native GitHub integration means no separate CI infrastructure to maintain. Matrix builds run tests across multiple PHP and Node versions in parallel.

Documentation Hub

How this hub is built

The documentation hub at rtvinc.github.io/docs is a static site served from the RTVInc/docs repository main branch via GitHub Pages.

Self-contained HTML files
Each document is a single .html file with all CSS, fonts, and images embedded as base64 data URIs. No build step, no node_modules, no CDN dependencies for user guides.

Field workers in rural Uganda need documents that work without internet. Self-contained files can be downloaded once and opened offline indefinitely.
GitHub Pages
Hosted directly from the main branch of RTVInc/docs. Commits to main are live within ~30 seconds.

No separate hosting infrastructure to maintain. Version history is the git log. Rollbacks are git reverts. Access control is GitHub org membership.
IBM Plex Sans
The primary typeface for all user guides and index pages — embedded as a base64 @font-face in the larger guide documents.

Clean, professional, and purpose-built for technical documentation. The monospace companion (IBM Plex Mono) is used for code blocks and API reference content.
RTV brand palette
Dark spruce (#183032) background with teal (#018793 / #4CB5BE) accents and amber (#EAB468) for highlights.

Dark theme reduces eye strain during field use on mobile devices in varying light conditions. Consistent with the RTV brand identity across all systems.
No JavaScript frameworks
Pure HTML and CSS for all structural and visual elements. JavaScript is used sparingly — only for the sidebar search, lightbox modal, and presentation navigation.

Zero build toolchain means any team member can open a file in a text editor and make a change. No framework upgrades, no dependency vulnerabilities to patch.
GitHub Releases for versioning
Significant updates are tagged as GitHub Releases (e.g. imp-v1.4.0) with all four guide files attached as downloadable assets.

Users who need a specific version for reference can download it directly. The release tag provides a stable permalink to a known-good state of the documentation.
Technical docs use CDN where appropriate
Architecture pages load Mermaid.js from a CDN to render infrastructure diagrams. Developer-facing reference pages are not used offline so this trade-off is acceptable.

Keeps the architecture docs maintainable — Mermaid source is readable plain text in the HTML, not pre-rendered SVG blobs.
